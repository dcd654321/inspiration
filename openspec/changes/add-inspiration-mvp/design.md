# Design

## 上下文

- 项目：`inspiration-miniprogram`，原生微信小程序（JavaScript / WXML / WXSS）+ 微信云开发。
- 现状：仅有工程骨架，无业务代码，无测试，云与 AI 均未启用（`config/cloud.js`、`config/ai.js` 的 `enabled` 为 `false`）。
- 参照：`yidian-miniprogram` 已验证的工程约定（OpenSpec 流程、`scripts/check.cjs` 结构检查、云函数产物与源码分离、账户级数据隔离）。

## 设计目标

1. 记录动作要快到几乎无成本：冷启动到落记录只允许一次输入加一次点击。
2. 原始灵感不可变，所有后续动作以追加方式发生。
3. AI 与照片都是可选增强，任一失效都不影响记录与浏览。
4. 数据归属清晰，删除可完全回收，不残留云端文件。

## 数据形态

沿用「一个账户一份文档」的形态，与 `yidian-miniprogram` 保持一致，减少跨项目认知成本。

集合 `linggan_accounts`，每个账户一份文档：

| 字段 | 说明 |
| --- | --- |
| `accountKey` | 由云函数可信上下文推导，不接受客户端传入 |
| `generation` | 数据代际，用于阻止已删除数据被离线旧设备回传 |
| `version` | 账户级版本号，用于冲突判定 |
| `inspirations[]` | 灵感数组 |

单条灵感：

| 字段 | 说明 |
| --- | --- |
| `id` | 客户端生成、服务端校验的稳定标识，用于幂等 |
| `text` | 原始正文，写入后不可变 |
| `createdAt` / `updatedAt` | 创建与最近更新时间 |
| `supplements[]` | 追加时间线，每项含 `id`、`content`、`createdAt`、`source`（`user` 或 `ai`） |
| `photos[]` | 图片记录，每项含 `id`、`fileId`、`createdAt` |
| `heat` | 最近一次热度计算结果缓存：`{ score, reasons[], computedAt }`。**本变更暂缓，字段保留但不写入**，见「热度设计」一节 |
| `deletedAt` | 软删标记，等待云端确认后才清理存储 |

云存储路径：`linggan/{accountKey}/{inspirationId}/{photoId}`。`accountKey` 参与路径，使越权拼接路径也无法命中他人对象，但**访问控制仍依赖云存储权限规则，不以路径命名代替隔离**。

## 云端资源范围

| 用途 | 资源名 | 本提案是否授予变更权限 |
| --- | --- | --- |
| 业务云函数 | `linggan_api` | 否，仅声明 |
| AI 云函数 | `linggan_ai` | 否，仅声明 |
| 账户集合 | `linggan_accounts` | 否，仅声明 |
| 云存储前缀 | `linggan/` | 否，仅声明 |

**部署授权**：创建集合、部署云函数、写入环境变量、开启 `cloud.js` 或 `ai.js` 的 `enabled`，均需在实施阶段单独取得用户明确授权。本设计不构成任何部署许可。

**回滚策略**：客户端开关回滚只需把 `enabled` 改回 `false` 并重新上传，不影响云端数据。数据侧回滚依赖 `generation` 递增：递增后旧设备的离线队列视为失效，不写回已清理的数据。云函数回滚保留上一版本部署记录，不删除集合与存储桶，避免不可逆的清空操作。

**不得自动迁移的数据**：用户既有的备忘录、聊天记录、历史截图等不在任何迁移范围内，只能由用户在应用内手动重新记录。

## 幂等与冲突

- 每条灵感、补充、图片记录都由客户端生成 `id`；服务端以 `(accountKey, id)` 为幂等键，重复提交只产生一次效果。
- 图片上传使用同一 `photoId` 作为存储对象名，重传覆盖同一对象而非新增。
- 账户级 `version` 冲突时停止自动写入并保留本机意图，由用户在页面明确处理，不自动合并或覆盖。

## AI 设计

- 模型调用只在 `linggan_ai` 云函数内完成，密钥通过云函数环境变量注入，**不进仓库、不进前端包**。
- 输出契约由 `miniprogram/core/ai-contract.js` 定义并校验：必需字段、字段类型、长度上限、结构完整性。校验失败按生成失败处理。
- 内容安全在云函数侧与客户端侧各过滤一次；命中规则的结果不展示、不写入。
- 额度按账户维度和单次会话维度双重限制，超限返回明确状态码，前端降级提示。
- 超时时间独立于业务函数，避免 AI 慢响应拖垮记录流程。
- **降级路径**：`ai.js` 的 `enabled` 为 `false` 时，前端不展示「AI 扩展」入口的实际调用，仅展示说明；记录、补充、拍照与浏览全部照常工作。

## 热度设计

> **暂缓（2026-09-22 决定）**：本节内容**不在本变更的实施范围内**，仅作为后续独立变更的设计依据保留。本变更内不实现 `core/heat.js`，不写入灵感数据中的 `heat` 字段（字段名保留以避免后续迁移），列表与详情页不出现热度展示位。以下描述不代表任何已实现行为。

热度分由本地确定性函数 `core/heat.js` 计算，输入全部是可核验的本机/云端信号：

| 信号 | 作用 |
| --- | --- |
| 距最近更新的时间 | 越久未动，活跃项权重下降 |
| 补充条数 | 用户反复回到这条灵感，说明在意 |
| 照片数量 | 有实物或场景佐证，信息更完整 |
| AI 扩展次数 | 用户愿意为它花生成额度 |
| 用户显式标记 | 直接表达优先级的信号，权重最高 |

规则：分数 = 各信号归一化后加权求和，输出 0—100 整数；理由由「命中了哪些信号、各贡献多少」直接生成，因此理由与分数天然一致。

**边界**：本地计算不依赖 AI，因此 AI 不可用时热度照常。当 AI 可用时，AI 只用于生成更细致的文字理由，**不直接决定分数**——分数仍由本地规则产出，AI 结果作为标注来源的补充说明。这样保证分数对同一份数据确定且可复现。

**措辞边界**：界面必须说明热度是排序辅助，不代表成功概率或收益预期。

## 非目标与已知取舍

- 不做全文检索与标签体系：MVP 阶段灵感量级有限，倒序列表足够；过早引入检索会牵出索引与同步复杂度。
- 不做分享与协作：与照片隐私边界冲突，且比赛期不依赖微信支付，无变现诉求。
- 不做外部热榜接入：热度只反映用户自己的行为，不伪装成外部事实。
- 热度不做趋势曲线：需要历史快照存储，收益低于成本，留待后续变更。
