# 修复云端备份与恢复闭环

## Why

当前云开关已打开，但客户端只在保存当下推送：待同步队列没有重试调度，也没有启动时拉取。客户端推送未带设计要求的 `baseVersion`，服务端又只在字段存在时才检查版本；删除走 `snapshot.push` 而不是具有照片清理语义的 `inspiration.delete`。本机快照和队列使用全局键，没有按当前可信账户隔离。这些缺口使「备份完成」「跨设备找回」「删除照片」和账户隔离都不能仅凭现有 Node 测试承诺。

## What Changes

- 以云函数可信上下文确认的账户为本机缓存作用域；用户已确认旧版没有须保留的真实记录，旧全局缓存只检测存在、不展示、不自动迁移或清理。
- 补齐拉取、带版本推送和待同步操作重试；服务端对必要的 `generation`、`baseVersion` 作强校验，冲突或代际落后时停止自动覆盖并保留可恢复的用户内容。
- 删除改用服务端 `inspiration.delete` 闭环，云文件清理成功后才向用户报告删除完成；失败时保留可解释的状态和重试入口。
- 向用户显示真实备份状态与可操作的恢复路径，不承诺尚未执行或无法保证成功的自动重试。

## Scope

仅处理本项目 `linggan_` 资源对应的客户端存储、云函数协议、仓库层及状态界面。继续使用可信微信身份与幂等请求 ID；不接受客户端传入的 AppID/OpenID 作为认证依据。具体资源、权限、迁移与部署步骤在实施设计和部署前核对。

## Non-goals

不自动合并两台设备对同一条灵感的不同改动，不清空或覆盖无法确认归属的旧缓存，不修改其他小程序资源，不启用照片或 AI，不在本变更内执行正式部署、生产迁移或发布。

## Acceptance

受控双账户、双设备测试能证明：内容只对所属账户可见；断网后恢复不会丢失或重复；冲突不会静默覆盖；删除时相关云文件按预期清理；备份状态与实际结果一致。自动测试、开发者工具、云端和真机证据分别记录。
