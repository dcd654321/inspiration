## 状态含义

| 状态 | 含义 |
| --- | --- |
| **已覆盖** | 有自动化测试断言了这条行为，测试名写在第四列 |
| **部分覆盖** | 有测试，但只覆盖了其中一部分（另一半在别的层，第四列写明缺哪一段） |
| **待验收** | **已实现，但只有人能验**——WXML/WXSS 渲染、真机交互，Node 里测不了。第四列写明要在哪验 |
| **待实现** | 还没有对应实现，第四列写清属于哪一层 |
| **已撤下** | 后续变更明确移除该功能，历史场景保留，当前发布包不计覆盖 |

第三列写「已覆盖」或「部分覆盖」时，第四列**必须以「测试名」开头**，名字要与 `tests/*.test.cjs` 里的完全一致——闸门会去核对它真的存在。

**「待验收」不是「已覆盖」的委婉说法。** 页面写完不等于验过：原型是 HTML、真实页面是 WXML，两者之间没有任何自动比对（`detailed-design.md` §0 已写明闸门管不到这件事）。在开发者工具里走通、并在 `VERIFICATION.md` 留下证据之前，这一条就只能停在「待验收」。

## 维护规则

1. **规范里加一条场景，这张表必须同步加一行**，否则 `npm test` 失败。
2. **实现一条场景**：领域层/服务层的改成「已覆盖」并写上测试名；只有人能验的改成「待验收」并写清在哪验。
3. **删掉一条场景，这张表里的行也要删**——陈旧条目同样会让测试失败。
4. 界面的场景在 `docs/ui-mockup.html` 里有原型，但**原型不等于验证**。页面写完了也仍停在「待验收」，直到在开发者工具里走通、并在 `VERIFICATION.md` 留下证据。
5. **「待验收」不能当「已覆盖」用。** 它存在的意义就是把「写完了」和「验过了」分开——两者混在一起，这张表就回到了它诞生之前的状态。
