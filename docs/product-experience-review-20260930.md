## 1. 产品与用户

**用户是谁。** 一个人，记自己的想法。没有协作、没有观众、没有社交关系。设计文档把这一点说得很准：「这个产品是一个人的私人灵感本」。

**在什么情境下用。**

| 情境 | 特征 | 对界面的要求 |
| --- | --- | --- |
| 想到一件事的当下 | 碎片时间、可能单手、注意力在别处 | 打开即能写，一次点击完成记录 |
| 几天后回来补充 | 已经知道这条是什么，来加一句 | 从列表到输入框的路径要短 |
| 需要用时来取 | 要一份能粘贴走的文字 | 出口明确，复制结果可预期 |
| 随手翻翻 | 没有目的 | 列表要能被扫读，不被控件挡住 |

**最重要的任务**：把一句话记下来 → 之后补充 → 需要时带走。

**第一次拿到实际价值的路径**（当前实现）：打开小程序（冷启动落在「记录」tab）→ 在输入框写一句 → 点「记下来」→ 云端确认 → 显示「已记下」→ 可点「查看这条」进入详情。这条路径**本身是通的，而且只有两次交互**，这是这个产品最有价值的部分。

**首次获得价值不需要**：登录页、授权弹窗、引导页、教程。当前实现里也没有——身份来自微信云函数上下文，没有额外的登录步骤。这一点做对了，不要改。

**哪些功能支持核心任务**：记录页、详情页（补充与时间线）、整理与留档、列表。
**哪些内容增加负担**：列表页首屏的四行筛选控件；详情页的「整理标记」整块表单；「我的」页的说明段落。

## 2. 产品体验判断

### 2.1 主要优势（应当保留，不要为了改版而改）

1. **原文是锚点。** 详情页把用户自己写的那句话放在全页最大字号（38rpx / 行高 1.78），不装进卡片，直接落在页面底色上。【观察：`08-detail.png`、`detail/index.wxss:13-20`】这是一个少见且正确的取舍——多数记录类产品会先给标题、标签、时间、操作，把用户写的话挤成一小段。这个产品反过来。
2. **保存的可信度设计。** 没有服务端确认就不清空输入、不报成功、不用会自动消失的 toast。对一个「记录」类产品，这是最重要的信任基础，比任何视觉修饰都值钱。【观察：`capture/index.wxml:32-47`、`docs/ui-design.md` §2】
3. **不可恢复的操作有真正的确认。** 删除补充的弹窗把**待删内容本身和时间**放进一个框里，正文写「此操作无法撤销」。【观察：`10-detail-confirm.png`】这让「要删的就是这条」是连着的，而不是两句不相干的话摆在一起。
4. **已合并内容可展开、可恢复。** 「默认隐藏 + 没有入口 = 删除」这条判断被认真执行了，列表的「已合并」筛选、详情的收起块都留了入口。【观察：`detail/index.wxml:149-177`、`list/index.wxml:15`】
5. **文案基调克制。** 整体没有营销腔，没有「让 AI 帮你」这类推销句式，也没有把工程流程端到用户面前。

### 2.2 核心障碍

1. **空数据时仍然展示全套控件。** 第一次打开「灵感」页，用户看到的不是「从这里开始」，而是一个**没有内容的控制台**：搜索框、四个筛选 chip、阶段筛选、每日回顾开关、选材整理按钮，然后才是「还没有灵感」。【观察：`32-firstrun-list-empty.png`】真正邀请用户开始的按钮落在屏幕下半部。
2. **详情页把主任务夹在中间。** 一页之内同时有：原文编辑、补充输入、五个动作按钮、「整理标记」表单（标签输入 + 阶段选择 + 保存）、照片区、时间线、删除。主任务是补充，但补充输入框下面紧接着五个按钮，然后是一整块 192px 高的表单——补充时间线的起点因此落在页面 941px 处，而可视区只有 671px：**首屏看不到任何一条已有的补充**。【观察 + 实测：`08-detail.png`、`26-detail-scroll1.png`】
3. **状态反馈的形状与颜色语义失守，外加一处布局崩坏。** 成功提示用的是**琥珀底色 + 感叹号**，与错误、警示共用同一个「!」图标，只靠底色区分——这正好违反产品自己写下的「不能仅依靠颜色传递状态」。同时，补充操作面板的「修改」「并入正文」被挤成逐字换行（`修` / `改` 各占一行）。【观察：`03-capture-saved.png`、`09-detail-sheet.png`】

### 2.3 最值得优先改变的三件事

| 顺序 | 改什么 | 为什么是它 |
| --- | --- | --- |
| 1 | 首屏减负：空数据时不渲染筛选与开关 | 直接影响「会不会用起来」。新用户第一次打开就看到一屏用不上的控件，是这个产品目前最大的第一印象损失 |
| 2 | 详情页重排：折叠「整理标记」、动作按钮等宽一行 | 详情页是使用频率最高的页面（每次补充都要进来），它的顺序决定了日常手感 |
| 3 | 反馈一致性修复：状态图标分形状、操作面板布局、空内容可提交 | 这三处都是「看起来像没做完」的细节，成本低、见效直接，且都是确定性缺陷 |

## 3. 问题与建议清单（按优先级）

优先级依据：**对核心任务的影响 × 出现频率 × 证据可信度 ÷ 改造成本**。

### P0 · 阻碍理解或操作

---

**P0-1　空列表首屏被控件占满**

- **页面**：灵感列表，无任何灵感时（也是新用户第一次进入这一页时的唯一形态）
- **问题**【观察】：即使 `items.length === 0`，页面仍然渲染搜索框、四个筛选 chip、「全部阶段 · 筛选」、「每日回顾」开关。这些控件此刻**没有任何可作用的对象**。空态卡与「记下第一个想法」按钮被推到屏幕下半部（`32-firstrun-list-empty.png`：在 390×844 上，「还没有灵感」出现在约 56% 高度处；空态卡之前有 4 行、约 250px 的控件）。
- **影响**：新用户在 3 秒内形成的印象是「这东西有好多设置」而不是「我可以开始写」。空数据时控件不是中性的，它们是**负向信息**——它们暗示这里本该有内容，而你没有。
- **建议**：`total === 0` 且无搜索词时，整块工具区（搜索、chip、阶段、回顾开关、选材整理）不渲染；只保留标题行、空态卡、「记下第一个想法」。
- **修改后**：`list/index.wxml` 的工具区与回顾开关包进 `wx:if="{{total > 0}}"`。空态下页面只有三个元素：标题 + 记一条、空态卡、主按钮。
- **收益**：新用户第一眼只有一件事可做。**代价**：几乎为零，纯条件渲染。**验证**：新用户看到列表页后能否在 5 秒内说出「下一步做什么」（见 §8 任务 T1）。

---

**P0-2　补充操作面板布局崩坏**

- **页面**：灵感详情 → 补充条目 →「更多」
- **问题**【观察 + 代码】：`09-detail-sheet.png` 里「修改」被拆成 `修` / `改` 两行，「并入正文」被拆成 `并入` / `正文` 两行，说明文字挤在右侧。根因在 `detail/index.wxss:258-278`：`.sheet-item` 用了 `display:flex; justify-content:space-between`，主标签与较长的 `.sub` 成为两个 flex 项，长文案把主标签压到逐字换行。「复制这条」没有副标签，因此被居中显示，与其余各项左对齐不一致。
- **影响**：这是用户**每次**修改、并入或删除补充都会看到的界面。逐字换行让操作名失去可读性，直接削弱「这一步会发生什么」的判断——而这正是这个面板存在的唯一理由。
- **建议**：`sheet-item` 改为块级、左对齐；`.sub` 另起一行放在主标签下方。改三行 CSS。
- **修改后**：主标签一行、说明紧随其下一行（视觉稿屏幕 6）。**收益**：面板立刻可读。**代价**：面板高度增加约 60rpx。**验证**：截图对比 + 真机点击。
- **附带**：「复制这条」不再居中，与其余项对齐。

---

**P0-3　详情页的信息层级：主任务被夹在中间**

- **页面**：灵感详情
- **问题**【观察 + 实测】：从上到下的顺序是 时间 → 原文 → 修改内容 → **继续补充（输入框 + 五个按钮）** → **整理标记（整块表单）** → 照片 → 补充时间线 → 删除灵感。「整理标记」是一个输入框 + 一个选择器 + 一个保存按钮的表单（`detail/index.wxml:86-91`），横在动作区和时间线之间。

  在 iPhone 12/13 Pro（可视区 671px）上实测的位置：

  | 区块 | 距页面顶部 | 说明 |
  | --- | --- | --- |
  | 动作按钮行 | 365px | 首屏内 |
  | 整理标记 | 551—744px | **高 192px**，跨在首屏底边上 |
  | 补充时间线 | **941px** | **首屏看不到任何一条已有补充**，需要滚动 270px |
  | 页面总高 | 1296px | —— |

- **影响**：这一页要回答两个问题——「我上次补充了什么」和「我要再加一句」。当前两者都被一块低频表单隔开。标签与阶段是**整理期**才关心的信息，却占据了每次进入的固定成本。
- **建议**：把「整理标记」由整块表单折叠成一行状态摘要，点击展开为表单；五个动作按钮改为一等宽的三个一组。
- **修改后**（视觉稿屏幕 5）：`整理标记　整理中 · 内容选题、城市散步　›` 一行约 44px；时间线因此上移约 148px（296rpx），第一条补充从「首屏下方 270px」变为「首屏下方约 122px」；动作区变为 `整理内容 | 复制内容 | 分享文字` 三个等宽按钮（AI 启用时另起一行）。
- **收益**：时间线离首屏更近（270px → 122px），低频表单不再拦截高频任务。**代价**：改标签需要多点一次（展开）。**验证**：从进详情页到看见时间线首条所需的滚动距离；补充一条的操作步数不变。

---

**P0-4　「整理标记」的标签输入框看起来不可编辑**

- **页面**：灵感详情 → 整理标记
- **问题**【观察】：标签是裸 `<input>`（`detail/index.wxml:88`），在白卡片里无边框、无底色、无输入提示符，渲染出来与静态文本完全一样——截图里「内容选题，城市散步」看起来就是一行说明文字。【观察：`08-detail.png`、`26-detail-scroll1.png`】
- **影响**：用户不会知道标签可以改。一个不可发现的编辑入口等于没有这个功能。
- **建议**：所有可编辑字段必须有可见输入边界（白底 + `1rpx` 边框或明显区别于正文的底色）。这条要写进实现约定，不只是改这一处。
- **修改后**：标签输入框带输入边界，占位符「标签，以逗号分隔，最多五个」在无值时可见。
- **收益**：标签功能从「隐藏」变为「可见」。**代价**：一行样式。**验证**：让用户指出详情页上哪些内容可以点击修改。

### P1 · 高频摩擦与不一致

---

**P1-1　成功、警示、错误共用同一个「!」图标**

- **页面**：记录页（保存成功）、列表页（刷新失败）、详情页（各类失败）、反馈页
- **问题**【观察 + 代码】：`app.wxss:168-218` 里 `.notice .mark` 是白字感叹号，三种语义（`notice-err` / `notice-warn` / `notice-success`）**只靠底色区分**。保存成功的琥珀底 + 感叹号，视觉上读起来像一条警告。【观察：`03-capture-saved.png`】
- **影响**：违反产品自己确立的「不能仅依靠颜色传递状态」；且成功被画成警告，让「记下了」这件事带上不确定感——而这个产品最不该动摇的就是这一刻。
- **建议**：三个语义用**三种形状**：成功 `✓`、警示 `!`、错误 `✕`；同时把成功反馈从琥珀色系改为主色系（琥珀色 `#e4a83a` 收回给品牌图形专用）。
- **修改后**：`✓ 已记下。查看这条`（主色底 + 主色文字）。**收益**：语义不再依赖颜色，色觉障碍用户同样可辨；琥珀色重新变成「灵光」的专属信号。**代价**：三个纯 CSS 图标（视觉稿已给实现）。**验证**：灰度截图下三种状态是否仍可区分。

---

**P1-2　反馈页空内容时提交按钮仍可点**

- **页面**：意见反馈
- **问题**【观察 + 代码】：`feedback/index.wxml:14` 的提交按钮只绑定 `disabled="{{busy}}"`，空输入时是完整的主色实心按钮；点下去才报「请填写 10 到 1000 字的意见。」【观察：`19-feedback.png`、代码 `feedback/index.js:33`】
- **影响**：与记录页「无内容即置灰」的规则直接冲突——同一个产品里，两个都是「写点东西再提交」的场景，行为却不同。用户学到的是「这个按钮能不能点要靠猜」。
- **建议**：`body.trim().length < 10` 时置灰，并把字数要求写在计数处（`3 / 10 字起`），而不是等提交失败才说。
- **收益**：提交前就知道要求。**代价**：一行条件。**验证**：用户是否会在空输入时尝试点击。

---

**P1-3　「每日回顾」用开关呈现，但状态存在内存里**

- **页面**：灵感列表
- **问题**【观察 + 代码】：开关默认开启（`services/discovery.js:37` 的 `enabled: true`），且状态存于 `createMemoryStorage()`（`app.js:5,107`）——**退出小程序即失效**。界面用的是 iOS 式开关，这个控件在用户认知里是「持久设置」。另外它占据列表页一整行，而它是一次性设定。【观察：`04-list.png`、`32-firstrun-list-empty.png`】
- **影响**：用户关掉再打开发现又开了，会认为设置没保存住（事实确实如此）。设计文档把「仅在当前会话生效」记为有意决策，但界面没有把这件事告诉用户，开关这个形态本身就在暗示相反的事情。
- **建议（两选一，推荐前者）**：①把开关移到「我的」，并在文案里说清它是本次使用期间有效；②保留在列表页但换成非开关形态（如回顾卡右上角的「不再提示」）。**无论选哪个，都不应该空数据时出现在首屏**（并入 P0-1）。
- **收益**：设置的去处符合预期。**代价**：改动小。**验证**：用户能否说出这个开关会/不会在下次打开时保留。

---

**P1-4　记录页副标题是功能罗列**

- **页面**：记录页（冷启动首屏）
- **问题**【观察】：副标题为「点子、计划和问题，都可以在这里记录、补充并整理使用。」这正是 `docs/ui-design.md` §6.1 第 1 条禁止的「功能罗列当卖点」写法——把「记录 / 补充 / 整理 / 使用」四个能力列了一遍。【观察：`01-capture-empty.png`】
- **影响**：首屏最贵的一行字用来说功能清单，而不是让用户动手。而且「整理使用」在这里无法兑现（要进详情页才知道怎么做）。
- **建议**：换成一句动作陈述，如「先写下来，之后再补充。」；把「之后能做什么」放到保存成功后（那时才有意义）。
- **收益**：首屏重心回到输入框。**代价**：一行文案。**验证**：首屏删掉副标题后，用户是否仍能说出产品用途（若不能，说明问题在主标题而非副标题）。

---

**P1-5　动作按钮落单**

- **页面**：灵感详情 → 动作区
- **问题**【观察】：`.output-acts .btn { width: calc(50% - 8rpx) }` 固定两列。AI 关闭时是 3 个按钮 → 第三行只剩「分享文字」一个（`aioff-02-detail.png`）；AI 开启时是 5 个 → 第三行只剩「汇总补充」一个（`08-detail.png`）。奇数个按钮时最后一个独占半行、左对齐，视觉上像漏了一个。
- **影响**：不是缺陷但是「没做完」的观感。这个区域是详情页的动作中枢，出现三次中的一次。
- **建议**：改为等宽 flex 一行三个（`flex: 1 1 0`），AI 按钮另起一行。
- **收益**：任何数量都不落单。**代价**：一行样式 + 按钮文案需控制在 5 字内（现文案最长 4 字，满足）。**验证**：AI 开关两种形态各截一次图。

**P1-6　成功提示里「查看这条」与正文分离**

- **页面**：记录页 → 保存成功
- **问题**【观察】：`capture/index.wxss:59-70` 的 `.result-link` 是 `display:flex` 块级元素，占满整行并左对齐，实际渲染成「正文一行 + 链接另起一行」。【观察：`03-capture-saved.png`】文案「已记下。可以继续记录，或查看刚才的想法。」本身也偏长，且「可以继续记录」是多余的——输入框已经清空并在等着了。
- **建议**：文案缩为「已记下。」+ 行内链接「查看这条」；`.result-link` 改行内元素，与文字同一行。
- **收益**：一行说清结果，一眼看到下一步。**代价**：两行代码。**验证**：用户能否在保存后 3 秒内找到刚记的那条。

### P3 · 可选

- **tab 命名语义不齐**：「记录」（动作）／「灵感」（对象）／「我的」（归属）三者不在同一维度。可考虑「记录／灵感／我的」保持不变——改动收益低于用户重新学习的成本；若要改，优先把「记录」改为「记一条」之类的动作短语，但收益有限。
- **间距散值**：`26rpx`、`36rpx`、`44rpx`、`52rpx` 等混用，建议收敛到 §7 的间距阶梯（这条属于实施规范，不影响当前体验）。

### 核心流程 A：记下一条（最高频）

              │
              ├─► 在输入框写一句

优化后
打开小程序 ──► 记录页（标题「记录想法」+ 一句「先写下来，之后再补充。」）
              │

## 5. 两个视觉方向与推荐

### 方向一「案头纸本」（推荐）

| 项 | 说明 |
| --- | --- |
| 气质 | 安静、可久看。像一本摊在桌上的纸本，界面尽量不发声 |
| 配色 | 暖纸底 `#f7f6f2` + 近黑墨 `#191a23` + 靛青主色 `#34377f`；琥珀 `#e4a83a` **只**出现在品牌图形里 |
| 字体层级 | 原文 38rpx / 行高 1.78 是全页最大的东西；页面标题 48rpx；区块标题 27rpx；正文 30rpx；辅助 26rpx |
| 布局特征 | 层级靠留白与发丝分隔线做，**全页没有投影**；承载面只用于输入区、列表、空态、面板；列表是连续的一块，不是一张张浮起的卡 |
| 适用原因 | 与产品承诺同向——「原文是锚点」需要一个不抢戏的容器 |

### 方向二「索引卡」

| 项 | 说明 |
| --- | --- |
| 气质 | 更快、更像工具。「我的灵感」读起来像一叠可以翻的卡片 |
| 配色 | 冷灰底 `#f4f5f7` + 白卡 + 1rpx 边框 `#e3e5ea` + 轻微投影；主色换成更饱和的 `#2f6bff` |
| 字体层级 | 整体降一档：正文 28rpx / 辅助 24rpx，一屏可看 6—7 条 |
| 布局特征 | 每条灵感是一张卡，左侧 6rpx 阶段色条（想法=灰蓝 / 整理中=琥珀 / 可使用=绿）；标签是填充 chip；强调「共 N 条 / N 条补充」这类计数 |
| 适用原因 | 如果产品未来要承载几百条以上、且以「扫视筛选」为主要行为，这个方向更合适 |

### 推荐「案头纸本」，理由具体如下

1. **内容规模不支持方向二的假设。** 个人灵感本的条目通常在几十到几百条之间。方向二的核心收益是「一屏多看几条」，这个收益在这个规模下用不上，而它的代价——每条都要描边、投影、色条——每一次打开都在付。
2. **颜色编码阶段会引入新的可访问性问题。** 方向二用色条区分「想法 / 整理中 / 可使用」，属于典型的「仅靠颜色传递状态」，仍然要在旁边补文字标签，反而更重。当前实现用文字标签（`item-tags`）是更朴素也更稳的做法，值得保留。
3. **迁移成本。** 现有实现已经接近方向一（暖底、无投影、原文最大、连续列表）。方向一需要改的是层级、间距与少数控件，不需要重做组件；方向二基本是一次重写。
4. **与既有设计承诺一致。** `docs/ui-design.md` §1 已经写下「原文是锚点」「层级用留白和分隔线做，不用阴影」「不滥用卡片把页面切成一格一格」。方向一是把这三条执行到位，而不是换一套主张。

**从方向二借一点**：列表项的阶段标签可以保留文字、但用**极轻的底区分**（视觉稿里用的是中性 `#edede7`），不作为主要识别手段——这是方向一框架内可以吸收的部分。

### 各屏幕的布局、按钮、文案与交互行为

**屏幕 1 · 记录页（首次进入）**
- 布局：品牌图形 + 「记录想法」+ 一句副标题，下方是输入卡片（min-height 由 216rpx 提到 300rpx），卡片内右下角为计数与主按钮。
- 主要按钮：「记下来」，无内容时置灰（`#e4e4ec` 底 + `#6f6f7b` 字）。
- 关键文案：副标题「先写下来，之后再补充。」；输入框占位符「此刻想到什么？」；卡片下一行小字「想到什么先写一句，之后可以继续补充、整理和复制。」
- 交互：输入即启用按钮；保存中按钮变「正在记下…」且输入框只读；成功后清空输入并显示屏幕 2 的反馈；失败保留输入，按钮恢复。

**屏幕 2 · 记录页（已记下）**
- 布局：输入卡片下方一行内联反馈。
- 关键文案：「已记下。查看这条」（对勾图标，主色系）。
- 交互：反馈常驻直到用户离开或再次输入；点「查看这条」进入刚保存的详情。

**屏幕 3 · 灵感列表（空）**
- 布局：标题行 + 空态卡 + 主按钮。**不渲染搜索、chip、阶段、回顾开关、选材整理。**
- 主要按钮：「记下第一个想法」，全宽主色。
- 关键文案：「还没有灵感 / 从一个想法开始，之后可以继续补充、整理并复制使用。」
- 交互：与记录页 tab 互通。

**屏幕 4 · 灵感列表（有条目）**
- 布局：标题行（我的灵感 + 记一条）→ 搜索框 → 一行 chip（全部 / 有补充 / 最近七天 / 已合并 / 阶段▾）→ 回顾卡 → 列表段落头（共 N 条 · 选材整理）→ 列表。
- 主要按钮：「记一条」（标题行文字按钮）。
- 关键文案：回顾卡「继续一个想法」+ 摘录 + 「继续补充」/「今天跳过」。
- 交互：「阶段」chip 打开选择面板；「选材整理」进入选材页；列表项整行可点，`hover-class` 保留。

**屏幕 5 · 灵感详情**
- 布局：时间 → 原文（38rpx）→ 修改内容 / 修改记录（N）→ 继续补充输入 → 三个等宽动作按钮 → 整理标记折叠行 → 补充时间线 → 删除灵感。
- 主要按钮：「添加补充」（输入框内右下）；动作按钮「整理内容 / 复制内容 / 分享文字」等宽。
- 关键文案：折叠行显示当前状态「整理中 · 内容选题、城市散步」，避免折叠后信息丢失。
- 交互：折叠行点击展开为表单并自动聚焦标签输入框；补充条目保留「更多」入口（长按仍可，但不作为唯一入口）。

**屏幕 6 · 补充操作面板**
- 布局：底部面板，标题行标明操作对象与时间；各项主标签在上、说明在下，左对齐；删除项用危险色并以分隔线隔开；底部独立的「取消」。
- 关键文案：「这条补充 · 09-27 11:02」；「并入正文 / 把这条补充追加到正文末尾，可展开恢复」。
- 交互：点遮罩或「取消」关闭；删除走二次确认（现有的确认弹窗保持不变）。

> **工具限制说明**：视觉稿是静态 HTML，不是可运行小程序。它精确到布局、间距、字号、颜色与文案，可直接据此实现；但**交互时序**（键盘顶起、滚动位置、动画）必须以真机为准。

## 7. 统一视觉规范与关键交互说明

完整表见 `docs/design-proposal-20260930.html` 末尾的「可执行视觉规范」。核心要点：

**颜色**：墨色三阶 `#191a23` / `#5f6070` / `#6f6f7b`；底色 `#f7f6f2`；承载面 `#ffffff`；线 `#e6e4de` / `#d7d4cb`；主色 `#34377f`（浅底 `#eeeef8`、描边 `#c9cae6`）；点睛 `#e4a83a` **仅限品牌图形与「当前」锚点标记**；错误 `#b43c32`；警示 `#8a6420`。
**新增约定**：成功反馈使用主色系，**不再使用琥珀色**——避免与警示混淆，并把琥珀还给品牌。

**字号**：48 / 38 / 31 / 30 / 27 / 26 / 24 rpx（页面标题 / 原文 / 列表正文 / 正文 / 区块标题 / 辅助 / 最淡）。行高 1.6—1.78，原文固定 1.78。字号不随屏幕缩放。

**间距**：0 / 8 / 16 / 24 / 32 / 40 / 52 rpx，不出现阶梯外的散值。页面左右 40rpx，底部 `calc(64rpx + env(safe-area-inset-bottom))`。

**圆角**：16 / 24 / 32 rpx（按钮与输入 / 卡片与承载面 / 底部面板上缘）。

**按钮**：高度 ≥88rpx。主 = 主色填充；次 = 白底 + `2rpx #d7d4cb`；安静 = 透明 + 主色字 + `2rpx #c9cae6`；危险 = 透明 + 错误色字 + 错误描边。**一行多个必须等宽**，禁止落单。禁用态必须有视觉区分，不能只靠逻辑拦截。

**表单**：一律白底卡片、`20rpx` 圆角、内边距 24—32rpx；**所有可编辑字段必须有可见输入边界**。

**列表**：单块承载面 + 发丝分隔线，行高 ≥120rpx，正文最多两行，元信息一行。

**图标**：不引入图标字体。状态图标三种形状 `✓` / `!` / `✕`，尺寸统一 30rpx 圆。

**状态反馈**：失败内联常驻，直到状态改变；成功内联，可随内容更新消失；进行中改按钮文案并置灰（「保存」→「保存中…」）；**不允许用会自动消失的 toast 报告失败**。

**关键交互约定**（延续现有实现，不改变）：
- 没有服务端确认就不清空输入、不显示成功。
- 草案（未写入）用虚线描边 + 「未写入」标注。
- 删除必须二次确认，且确认框里出现待删内容与时间。
- 已合并内容默认收起但**必须有展开入口**。
- 正常同步的条目不带任何标记，同步异常才出现标记。

## 9. 验收与用户测试方案

分三层报告，三层的结论不能互相代替。

### 第一层：设计检查（本轮已完成）

| 结论 | 内容 |
| --- | --- |
| 已观察到的 | P0-1…P0-4、P1-1…P1-6、P2-1…P2-6 全部有截图或代码依据 |
| 基于设计经验的判断 | 详情页顺序、列表控件密度、「我的」页文档式排版——这些没有用户数据支撑，属于专业判断 |
| 需要验证的假设 | 折叠「整理标记」不会让用户找不到标签入口；把每日回顾移到「我的」不会让用户找不到它；chip 行合并后阶段筛选仍可被发现 |

### 第二层：原型测试（视觉稿阶段即可做，5—8 人）

| 任务 | 成功标准 | 需要先测基线吗 |
| --- | --- | --- |
| T1 首次理解 | 看到记录页 5 秒后，能说出「这是记自己想法的工具」；能指出从哪里开始 | 需要。当前无数据，先测现状 |
| T2 完成记录 | 从打开到保存成功 ≤ 2 次交互，无求助、无误触 | 不需要，路径未变 |
| T3 空态起步 | 无灵感时打开「灵感」页，能指出下一步做什么（目标：不出现「这里没有东西可以点」） | 需要。这是改动的主要目标 |
| T4 补充一条 | 从列表进入某条 → 看到补充输入框，不需要滚动超过一屏 | 需要。当前需滚动 |
| T5 取用文字 | 把一条灵感变成可粘贴的文字 ≤ 3 步，且能说出「已经复制了」 | 不需要 |
| T6 状态辨识 | 灰度打印/灰度截图下，仍能区分成功、警示、失败三种提示 | 不需要，改动后重测 |
| T7 视觉方向偏好 | 在两份视觉稿之间选择，并说明理由（记下原话，不要只记选项） | —— |
| T8 二次进入 | 隔一天再打开，能在 10 秒内找到上次那条 | 需要基线 |

**记录什么**：犹豫的时长、误触的位置、回退的次数、求助的原话。**不要只记「完成/未完成」**——完成但犹豫 20 秒和顺畅完成是两件事。

### 第三层：真实用户验证（有上线条件后）

- 真机验证清单：iOS/Android 各一台；窄屏与大字号；键盘顶起时输入框是否被遮挡；相册权限拒绝后的提示；弱网下保存失败的恢复路径。
- 多账户：两个微信账户、两台设备的数据隔离与跨设备一致性（这是安全验收，不是体验验收，分别报告）。
- **只有在拿到真实数据之后**，才能谈论完成率、留存或推荐意愿的变化。本轮所有建议都是基于界面证据与设计推理，**没有任何数据可以支持「提升了 X%」的说法**。

**原文衬线这条要特别说明**：它不在原报告的视觉规范里（规范只写了靠字号区分），是审查后在对话里追加的三条「提升辨识度」建议之一，属于**需要看过再定**的改动。Android 多数机型没有中文衬线字体会回落到无衬线——是降级不是损坏，但两端观感不同，真机上要分别看过；不满意的话删掉那一行 `font-family` 即可回到原样。

### 实施中发现的新问题

**小程序 `button` 的默认样式会盖掉单类选择器里的 `width`、左右 `margin` 和左右 `padding`。** 表现是按钮被撑成 184px 宽居中，文字在框里居中——「记一条」「更多」这类链接式按钮离右边距有 80px 空档；补充操作面板的条目缩成一条居中的窄列；筛选 chip 也比设计值宽。这一条在改动前就存在，旧截图里能看出来。

修法是**用两层选择器**：`app.wxss` 里加了 `.page button / .welcome-page button / .viewer button { width: auto; margin-left: 0; margin-right: 0 }` 统一复位（只动宽度和左右外边距，不碰上下外边距，否则会清掉 `.save-btn` 自己的间距），其他需要覆盖的地方各用两层选择器（`.sheet .sheet-item`、`.notice .result-link`、`.list-filters .filter-chip`）。

**还有一处连带影响值得记下**：整宽按钮的规则原来是 `.page .btn-block`，欢迎页没有 `.page` 祖先，加上复位后两个按钮退化成并排。已改成 `.btn.btn-block`（两层，且所有用法都同时带 `.btn`），并补了断言。

**今后给 `<button>` 写宽度、左右外边距或左右内边距，一律用两层选择器**，否则改了不生效、而且不报错。

### 尚未实施

- **间距阶梯的全局归一化**（报告 §7 的 `0 / 8 / 16 / 24 / 32 / 40 / 52 rpx`）。报告里本就标为「不影响当前体验」的可选项；它要改十几个文件的几十处数值，没有用户可见收益，却可能悄悄改掉既有版式的呼吸感。**建议不做**，或等有明确的版式问题再局部处理。
- **tab 图标重画**。当前三个是通用线性图标，与「拾光」意象无关。重画需要生成新的图片资源（`scripts/build-tab-icons.ps1`）并逐尺寸看过，适合单独一轮，不适合夹在样式收敛里。
- 第二批、第三批的改动都在 WXML/WXSS 与页面逻辑层，**渲染效果只在本机开发者工具模拟器上核过**（`docs/evidence-20260930-after/`），真机、键盘顶起、系统大字号仍未验证。

`AGENTS.md`、`README.md`、`openspec/changes/add-inspiration-mvp/design.md` 三个文件的改动是本次工作之前就存在的，未由本次改动触碰。
