# 灵感拾光簿 UI / UX 整改审阅

> 审阅日期：2026-09-22  
> 审阅范围：`miniprogram/app.*`、五个页面的 WXML / WXSS / JS、`docs/ui-design.md`、`docs/ui-mockup.html`、OpenSpec 设计与现有规范覆盖表。  
> 本文先记录审阅基线，再记录整改实施。2026-09-22 已完成第一版代码整改；自动检查已通过，真实 WXML / WXSS 渲染与真机验收仍待微信开发者工具完成。

## 1. 审阅结论

当前版本的领域逻辑、数据保护意识和失败分支明显强于界面完成度。记录、编辑、历史、补充、合并与删除的底层规则较完整，但用户看到的产品仍偏“内部 MVP”：视觉辨识度弱，部分功能入口难发现，异步状态不完整，多处工程术语直接暴露给用户，详情页还长期展示尚未开放的能力。

建议先解决状态误导、危险操作、重复提交和可访问性问题，再做品牌化视觉升级。只换颜色、圆角或图标，不能解决当前最影响使用信心的问题。

### 1.1 综合判断

| 维度 | 当前判断 | 主要原因 |
| --- | --- | --- |
| 产品定位 | 清楚 | “随手记录 → 持续补充 → 回看历史”主价值明确 |
| 信息架构 | 基本合理 | 记录、列表、我的三个 Tab 易理解；详情承载内容过多 |
| 易用性 | 需要整改 | 长按操作难发现，重复提交缺少拦截，部分失败态呈现错误 |
| 视觉完成度 | 偏低 | 视觉语言通用、品牌识别弱、缺少图标与细节反馈 |
| 文案 | 需要统一 | “云端、时间戳、标识”等工程词进入用户界面；部分措辞生硬 |
| 可访问性 | 风险较高 | 小按钮不足 44px、浅灰文字对比度不足、多个 `view` 充当按钮 |
| 上线成熟度 | 尚不适合直接发布 | 照片、AI、云同步未形成完整可用闭环，真机视觉与交互未验收 |

### 1.2 最值得保留的设计

- 记录页把主要任务收敛到一个输入框和一个保存动作，方向正确。
- 详情页让原文成为视觉锚点，没有把所有内容切成卡片，适合个人笔记产品。
- 原文修改保留历史，且历史没有删除入口，产品承诺明确。
- 保存失败保留输入、同步失败不谎报保存失败，数据状态意识较好。
- 删除补充采用二次确认，并在弹窗中展示待删除内容，能降低误删风险。
- AI 结果明确标识来源，未启用时不会伪造结果。
- 全局样式集中在 `app.wxss`，具备继续建设设计令牌和组件规范的基础。

## 2. 证据边界

本次结论分成三类：

1. **代码确认**：可直接从 WXML、WXSS、JS 的条件、文案、尺寸和状态分支确认。
2. **设计意图确认**：来自 `docs/ui-design.md` 与 `docs/ui-mockup.html`，不代表真实小程序已经按该效果渲染。
3. **待真机确认**：字体缩放、键盘顶起、长按手势、弹层焦点、图片网格、窄屏和不同机型安全区。

浏览器安全策略阻止了本地 `file://` 原型页面的截图捕获，本次没有把 HTML 原型截图当成视觉证据；微信开发者工具和真机也未运行。因此本文是**基于代码与设计文档的 UI / UX 整改审阅**，不等同于已完成真实渲染视觉验收。

## 3. 用户流程健康度

| 步骤 | 用户目标 | 当前健康度 | 主要问题 |
| --- | --- | --- | --- |
| 1 | 打开后快速记下一条灵感 | 基本健康 | 输入框没有聚焦策略；主按钮未按设计做成全宽；空白输入仍会亮按钮 |
| 2 | 确认保存结果 | 有风险 | 成功仅用短暂 Toast；同步失败文案暴露“云端”；异常提示可能残留 |
| 3 | 浏览已有灵感 | 有明显缺口 | 首次读取失败会被呈现为普通空列表；列表缺少同步/冲突状态与点击反馈 |
| 4 | 打开并补充灵感 | 基本可用 | “提交”过于表单化；没有提交中状态；长按操作入口难发现 |
| 5 | 修改、合并、恢复补充 | 难发现 | 关键操作全部依赖长按；“合并进灵感”含义模糊；操作中无法防重复点击 |
| 6 | 回看原文历史 | 基本健康 | 当前版本放在长列表底部；“早期版本/被替换”措辞生硬；缺少比较辅助 |
| 7 | 删除补充或整条灵感 | 有风险 | 删除灵感确认没有说明照片也会删除；异步删除没有明确进行中状态 |
| 8 | 理解数据与隐私 | 容易误解 | 云开关与云端资源验收不是一回事；原页写“存在你的账号里”，容易让人误以为备份已可用 |

## 4. 必须优先整改的问题

### P0-01 首次读取失败会被伪装成“还没有灵感”

**代码证据**

- `pages/list/index.js` 在存储未准备好或读取失败时设置 `error`。
- `pages/list/index.wxml` 先判断 `items.length === 0`，错误提示只写在有列表数据的 `wx:else` 分支内。

**用户后果**

用户看到“还没有灵感”，会误以为数据丢失或从未保存，而不是一次读取失败。这是当前最严重的状态误导。

**整改要求**

- 空数据与读取失败必须是两个独立状态。
- 无缓存且读取失败时显示“暂时无法读取灵感”及重试按钮。
- 有缓存但刷新失败时继续显示缓存，并在列表上方显示非阻断提示。
- 错误态不得同时出现“还没有灵感”。

### P0-02 删除灵感的确认内容不完整

**代码证据**

`pages/detail/index.js` 的确认文案为“这条灵感与它的补充将被移除”，没有说明关联照片也会被删除；实际设计和服务端语义要求删除照片。

**用户后果**

用户无法在确认前理解完整影响范围，尤其是照片属于个人内容且删除不可恢复。

**整改要求**

确认文案改为：

> 确定删除这条灵感吗？正文、补充和照片都会删除，且无法恢复。

若照片清理失败，界面必须明确说明“删除未完成”，不得先返回列表并给出成功印象。

### P0-03 多个异步操作缺少进行中状态与重复点击保护

**代码证据**

- 记录页有 `saving`，但原文修改、补充提交、补充修改、合并、恢复、删除补充和删除灵感均没有独立 pending 状态。
- `pages/detail/index.wxml` 的“保存”“提交”“恢复”“删除”等操作没有按异步过程禁用或改文案。

**用户后果**

弱网或设备卡顿时，用户会反复点击；即使底层具备部分幂等能力，界面仍会给出“不知道是否点成功”的体验，还可能重复弹层、重复 Toast 或覆盖状态。

**整改要求**

- 每类写操作有独立 pending 状态，不使用一个全局 loading 阻塞整页。
- 按钮文案明确变化，例如“添加”→“添加中…”、“删除”→“删除中…”。
- 操作执行期间禁用同一动作，其他阅读和滚动不受影响。
- 异步结束后才关闭弹层；失败时保留用户输入和操作上下文。

### P0-04 数据归属文案与当前能力状态矛盾

**代码证据**

- `config/cloud.js` 已打开，但集合、云函数与权限规则是否在目标环境中可用，单靠代码无法确认。
- 整改前“我的”页把内部云开关显示成用户可见的能力状态，同时写“灵感和补充存在你的账号里”。
- 删除失败和同步提示直接提到“本机/云端”的实现分层。

**用户后果**

用户无法判断换设备后是否还能看到数据，也无法判断“账号里”是否代表已经备份。当前措辞容易形成跨设备可恢复的错误预期。

**整改要求**

- 在云端资源与权限未验收前，不宣称数据已经保存在账号中或仅本人可访问。
- 面向用户只描述结果，不描述“本机快照、队列、云端”等内部结构。
- 若提供备份状态，应使用“自动备份”这一用户概念，并给出可验证状态和失败后的处理入口。

### P0-05 内部异常信息可能直接展示给用户

**代码证据**

`core/errors.js` 声明这些文案可直接展示，其中包含：

- “标识格式不正确”
- “时间戳不正确”
- “缺少原文历史标识”
- “原文历史标识重复”
- “汇总的写入方式不正确”
- “图片标识不正确”

**用户后果**

用户无法据此采取行动，反而会认为数据损坏或产品不可靠。

**整改要求**

- 领域错误码与用户文案分层，页面不得直接渲染内部错误词典。
- 可由用户修正的错误说明具体动作，例如“正文最多 2000 字”。
- 不可由用户修正的内部异常统一为“操作没有完成，请返回后重试”，技术细节仅进入诊断记录，且不得包含用户正文或照片。

## 5. 易用性问题清单

### P1-01 长按是核心操作的唯一入口，发现性过低

正常补充没有任何“可操作”提示，只有用户已经展开隐藏补充时才看到“长按可恢复或删除”。修改、并入正文、删除这些高频或高风险操作都依赖长按，不符合大多数用户对笔记产品的预期。

**整改方向**

- 每条补充右侧提供可见的“更多”图标按钮，点击后打开操作面板。
- 长按可以保留为快捷方式，但不能是唯一入口。
- “更多”按钮需要至少 88rpx 触摸区域和明确的 `aria-label`。

### P1-02 “合并进灵感”难以理解

补充本来就属于这条灵感，“合并进灵感”无法说明到底合并到哪里，也与 AI 汇总中的“合并”混淆。

**整改方向**

- 主文案改为“并入正文”。
- 辅助说明改为“把这条补充追加到正文末尾”。
- 被收起后的状态改为“已并入正文”，避免“灵感”同时指整条记录和正文区域。

### P1-03 详情页长期展示两个不可用模块

“照片还不支持添加”和“AI 扩展还没开放”会让详情页显得像演示版本，并把用户注意力从记录与补充主流程带走。

**整改方向**

- 功能不可用时直接隐藏整个区块。
- 只有确定即将开放且需要收集意向时，才设置一次性的“即将支持”说明；当前产品没有这一需求。
- 功能启用后再按完整状态接入，避免先放空壳入口。

### P1-04 记录页按钮逻辑与空白输入不一致

按钮只判断 `draft.length === 0`。输入空格后按钮可用，点击却无反应，用户会认为按钮失效。

**整改方向**

- 禁用条件按 `trim()` 后的长度判断。
- 补充输入和行内编辑采用相同规则。
- 不要依赖点击后的静默 `return` 纠正界面状态。

### P1-05 详情页错误提示可能长期残留

`persist()` 在同步失败时设置页面 `error`，后续同步成功没有统一清空；`load()` 也不重置通用错误。用户可能完成下一次成功操作后仍看到上一条红色提示。

**整改方向**

- 每次新操作开始时只清理与该操作相关的旧错误。
- 成功后明确清理对应错误。
- 页面级错误、原文错误、补充错误、照片错误分别归属，不共用一个容易残留的字符串。

### P1-06 列表缺少真实状态标记

设计文档要求在同步失败、冲突、删除中显示状态，但 `decorate()` 只输出正文、时间、补充数和照片数。

**整改方向**

- 只展示需要用户关注的状态：“备份失败”“有冲突”“删除中”。
- 正常保存和短暂待同步不加徽标，避免状态噪音。
- 状态标签点击后应解释下一步，而不是只显示颜色。

### P1-07 列表底部“新建灵感”不适合长列表

列表内容多时按钮在最底部，很难到达；虽然底部已有“记录”Tab，但两个入口没有形成清晰主次。

**整改方向**

- 保留“记录”Tab 作为主入口。
- 列表页右上角增加小型“记一条”入口，或在滚动时保留轻量悬浮按钮。
- 删除列表末尾重复的大按钮，避免页面尾部视觉拖沓。

### P1-08 当前列表行缺少可点击反馈与方向提示

列表整行可点击，但没有 `hover-class`、箭头或其他进入详情的视觉暗示。

**整改方向**

- 增加按压反馈，颜色变化要轻，不使用缩放造成列表跳动。
- 右侧可使用细小箭头；若正文占满两行，箭头垂直居中并保持独立空间。
- 整行保持大触摸区域，不让用户只能点文字。

### P1-09 当前版本放在历史长列表底部，不利于比较

版本多时，用户进入页面先看到旧内容，却需要滚到底部才知道现在的正文是什么。

**整改方向**

- 当前正文放在顶部，使用浅品牌色承载面标记“当前内容”。
- 下方按时间倒序展示修改记录。
- MVP 不必实现复杂 diff；可先增加“修改于 YYYY-MM-DD HH:mm”和版本序号。

### P1-10 “我的”页缺乏用户价值

页面主要展示内部能力开关，用户无法操作，也无法解决问题。它更像开发状态页，而不是产品页面。

**整改方向**

- 删除“能力”模块。
- 保留“数据与隐私”“反馈”“关于灵感拾光簿”。
- 自动备份正式开放后，再加入可操作的“备份状态”和“立即重试”，不要只显示“已启用/未启用”。

## 6. UI 与视觉完成度整改

### 6.1 当前视觉的主要不足

1. **品牌弱**：页面以冷灰、白色和单一靛蓝构成，与任何通用效率工具都很相似。
2. **底部导航弱**：`app.json` 只有文字 Tab，没有图标，与原型中的图标导航不一致。
3. **空态不完整**：设计文档要求文档线描图标，代码只有文字和大面积白卡。
4. **加载态陈旧**：用完整空卡承载“读取中…”，视觉重且容易与空态混淆。
5. **层级偏平**：列表正文、元信息、区块标题依赖字号和浅灰色区分，缺少品牌性的细节锚点。
6. **交互反馈少**：列表行、隐藏内容入口、自定义弹窗按钮都缺少可见按压态。
7. **大量固定小字号**：多个 22—24rpx 文字在高密度屏和大字号环境下可读性不足。

### 6.2 推荐的视觉方向：纸页上的一束灵光

品牌名称现为“灵感拾光簿”；已生成头像中的视觉语言应延伸到产品，而不是只在平台头像上使用：

- **背景**：由冷灰改成轻微暖调的纸张白，减少工具感。
- **主色**：保留深靛蓝，承担主按钮、选中态和关键链接。
- **点睛色**：加入少量暖金，只用于保存成功、灵光标记、空态插图和品牌细节，不用于普通正文。
- **承载面**：白色或接近白色；减少“每块内容都是卡片”的感觉。
- **圆角**：只保留 12px、16px 两档，弹层可用 20px；避免每个元素都做成大药丸。
- **阴影**：页面内容不使用常驻阴影；弹层可用轻阴影区分层级。
- **图标**：使用一套线性图标，笔触与微信原生风格接近；不混用 Emoji、字符图标和多套图标库。

建议令牌方向，仅作为后续设计输入：

| 用途 | 建议值 | 说明 |
| --- | --- | --- |
| 页面底色 | `#F7F6F2` | 比现有冷灰更像纸张，仍保持干净 |
| 正文 | `#191A23` | 保持高对比 |
| 次要文字 | `#5F6070` | 适合说明文本 |
| 最淡可读文字 | `#6F6F7B` | 在浅背景上约 4.56:1，优于现有 `#9B9BAA` |
| 主色 | `#34377F` | 延续现有靛蓝，略微收敛饱和度 |
| 灵光金 | `#E4A83A` | 仅做品牌点睛，不承载小字号文字 |
| 危险色 | `#B43C32` | 用于删除和明确错误 |
| 分隔线 | `#E6E4DE` | 与暖纸色协调 |

### 6.3 “流行感”应该从哪里来

本产品适合“编辑式、安静、个人化”的笔记风格，不适合堆叠玻璃拟态、彩色渐变和高饱和运营卡片。更耐看的现代感来自：

- 更大的主标题和正文，减少小字堆叠；
- 更少的框线和卡片，用留白建立层级；
- 一套统一线性图标；
- 160—220ms 的轻量状态过渡，例如保存成功、展开收起和底部操作面板；
- 骨架屏替代“读取中…”大卡；
- 对关键动作给明确的按压、进行中、成功和失败反馈；
- 空态使用与头像同源的书页与灵光图形，保持品牌记忆。

“流行”不应以牺牲微信内一致性为代价。微信官方 WeUI 的定位就是让小程序与微信原生体验保持一致，操作面板、对话框、上传、Toast、导航和反馈可优先参考其组件与层级规范：[WeUI](https://weui.io/)。

## 7. 分页面整改方案

### 7.1 记录页

**保留**

- 页面只做记录，不添加教程、运营位或功能介绍。
- 输入卡片大面积留白。
- 字数接近上限时再提醒。

**整改**

- 标题改得更开放，避免让用户以为只能写一句话。
- 明确输入框聚焦策略：用户从“记一条”入口进入时自动聚焦；普通切换 Tab 时不强制弹键盘。
- 保存按钮改成输入卡片内全宽主按钮，与设计文档保持一致。
- 90% 字数提示使用警示色，不使用错误红色。
- 保存成功后在页面内短暂显示“已记下”，并提供“查看这条”轻入口；Toast 可保留但不作为唯一反馈。
- 空白字符不点亮按钮。

**推荐结构**

1. 标题“记下此刻的想法”
2. 辅助语“没想完整也没关系，先记下来。”
3. 大输入区
4. 字数与错误提示
5. 全宽按钮“记下来”

### 7.2 灵感列表页

**整改**

- 先修复空态与错误态冲突。
- 加入骨架加载，不再用空卡显示“读取中…”。
- 页头显示“我的灵感”和轻量“记一条”入口。
- 列表项增加按压反馈和进入详情的方向提示。
- 照片功能接通后，有照片的条目可显示一张 56—64px 缩略图；无图条目保持纯文本，不能放统一占位图。
- 元信息最多保留时间、补充数、照片数和异常状态，不显示内部同步过程。
- 暂不增加搜索、标签、排序筛选。当前数据规模和提案范围不支持这些功能，添加只会让产品显得复杂。

### 7.3 灵感详情页

**整改**

- 原文继续作为最大视觉锚点。
- “编辑原文”改为“修改内容”；“历史版本”改为“查看修改记录”。
- 补充条目增加可见的“更多”按钮，长按降为快捷操作。
- “提交”改为“添加”，并增加提交中状态。
- 收起内容的两种状态明确区分：“已并入正文”和“原补充已收起”。
- 未启用的照片和 AI 区块整体隐藏。
- 删除灵感与正文、补充编辑区拉开更大距离，放在页面底部的“更多操作”区域。
- AI 生成的补充除了标签，还应有可感知的说明“请核对内容”；不要只靠颜色区分。

### 7.4 历史版本页

**整改**

## 8. 可访问性与适配风险

### 8.1 触摸区域不足

`app.wxss` 约定触摸目标不小于 88rpx，但：

- `.btn` 高度为 80rpx，约 40px；
- `.btn-sm` 高度为 68rpx，约 34px；
- 注释声称“由 padding 补足”，但垂直 padding 为 0，没有补足高度。

所有按钮、列表更多操作、收起行和弹窗操作都应保证至少 88rpx 的有效点击高度。

### 8.2 浅灰文字对比度不足

按代码色值计算：

| 前景 / 背景 | 对比度 | 风险 |
| --- | --- | --- |
| `#9B9BAA` / `#F5F5F8` | 2.52:1 | 小字号时间、占位符难读 |
| `#9B9BAA` / `#FFFFFF` | 2.74:1 | 列表元信息难读 |
| `#D29B95` / `#FFFFFF` | 2.37:1 | 删除辅助说明难读 |
| `#5F5F6E` / `#FFFFFF` | 6.27:1 | 可保留 |

未执行完整 WCAG 合规测试，但这些浅色小字明显存在风险。普通小字号文字应以 4.5:1 为目标；装饰性元素可以更浅，但不能承载关键状态。

### 8.3 字号偏小

22—24rpx 大约等于 11—12px，当前被用于标签、区块标题、时间、提示和弹层说明。建议正文辅助信息不低于 26rpx，关键状态不低于 28rpx，并在开发者工具中验证系统大字号。

### 8.4 自定义 `view` 充当按钮

操作面板、隐藏行和自定义确认弹窗大量使用 `view bindtap`。视觉上能点击，不代表读屏或键盘焦点能正确识别。

建议优先使用 `button` 或补齐语义、可访问名称、焦点顺序与禁用状态。弹层打开后还需验证焦点是否停留在弹层内，关闭后是否回到触发控件。

### 8.5 只靠长按和颜色传达状态

- 长按对运动能力受限、首次使用和读屏用户不友好。
- AI 时间线圆点、启用状态与错误状态部分依赖颜色。

必须同时提供可见文字、图标和明确入口。

## 10. 设计文档与实现不一致

以下差异会让后续维护继续跑偏，应在真正实施整改时一起处理：

| 设计约定 | 当前实现 | 风险 |
| --- | --- | --- |
| 记录页主按钮为全宽 | 当前与字数计数并排，是内容宽按钮 | 原型、文档和真机三套效果 |
| 列表空态带线描图标 | 当前只有文字 | 空态显得未完成 |
| 列表展示异常同步状态 | 当前没有状态字段 | 用户无法识别冲突或失败 |
| 列表有“选择”和已合并入口 | 当前未实现 | AI 汇总和恢复链路不完整 |
| 详情有照片网格与 AI 草案 | 当前只显示“未开放”说明 | 页面结构长期被空壳占据 |
| AI 内容需明确“可能不准确” | 已保存的 AI 补充只有“AI 生成”标签 | 风险提示不足 |
| 所有异步按钮有进行中文案 | 详情页多数写操作没有 | 重复点击和状态不确定 |
| 触摸目标不小于 88rpx | 普通按钮 80rpx，小按钮 68rpx | 设计令牌未真正执行 |

## 11. 整改优先级与实施顺序

### 第一阶段：上线前必须完成

1. 修复列表读取失败与空态冲突。
2. 补齐删除灵感的照片影响说明和失败状态。
3. 给详情页全部写操作增加 pending、禁用和防重复点击。
4. 分离内部错误与用户文案。
5. 修正数据归属和备份文案；云端资源与权限验收前不暗示已经跨设备保存。
6. 把普通按钮和小按钮的有效触摸区域提升到至少 88rpx。
7. 把关键浅灰文字对比度提升到可读水平。
8. 隐藏未启用的照片和 AI 区块。

### 第二阶段：完成核心体验

1. 用可见“更多”按钮替代只靠长按的操作入口。
2. 补齐列表异常状态、按压反馈和方向提示。
3. 统一记录、补充和编辑的输入校验与进行中反馈。
4. 重构“我的”页，移除开发状态展示。
5. 调整历史页信息顺序和文案。
6. 接通照片后再展示照片区；接通 AI 完整确认流程后再展示 AI 区。

### 第三阶段：视觉品牌化

1. 确认最终小程序名称，并统一平台名称、导航栏标题、代码描述和关于页。
2. 把头像的靛蓝、暖金、书页元素扩展为设计令牌和空态插图。
3. 补齐 Tab 图标、空态图标和统一线性图标系统。
4. 使用骨架加载、轻量过渡和按压反馈提升完成度。
5. 在微信开发者工具中逐页对照原型，再做 iOS、Android、窄屏和大字号真机验收。
